## 问题：市面上的 AI 陪伴项目，为什么总让人觉得"不对"？

几乎所有 AI 聊天伴侣都有同一个底层缺陷：**现在的LLM总是被RL训练成"助手"或者"奴隶"——看到的**每一条**输入都必须生成**一条**回答，且倾向于完整、正确、礼貌、可执行。** 靠 prompt 告诉它"别像客服"，只会让它变成畏手畏脚且冷淡敷衍的客服。

诸多痛点无法靠prompt/SOUL.md来稳定解决：

| 表面现象 | 根因 |
|---|---|
| 每句话都接，从不沉默 | LLM 天然倾向 `有输入 → 有输出` |
| 回复总像答题/员工/咨询师 | LLM训练本身目标偏"完整可执行" |
| 主动消息像运营召回 | 用提醒逻辑和cosplay做陪伴 |
| 记忆架构沉重且可控性极弱 | 记忆架构设计远远比存储召回方式更重要 |
| 表情包驴唇不对马嘴 | 表情包的存储召回方式过于简单 |


<h2 align="center"><i>这个项目不是让 LLM 更会回答，而是让系统更会相处。</i></h2>
<h3 align="center"><i>全部架构由人类设计</i></h3>
---

## 核心洞察

```
在不训练新模型的情况下依靠harness来攻克以上困境，真的可行吗？ 
问题不在 LLM 不够聪明不会思考，而在于架构不允许它"不回答"。
```
 
不只依赖复杂 prompt，我们做了一个关键转变：

> **LLM 仍然可以思考、判断，但只有只有结构对、状态对时，用户才看到回复。**

```
之前：用户输入 → LLM 生成 → 用户一定看到文本
之后：用户输入 → LLM 生成 { action, items } → 协议层校验 → 转发层判断 items 是否可见 → 用户可能看到消息
```

这个看似微小的架构变化，打开了一系列真正不同的行为：

- LLM 可以选择 `WAIT`，等用户说完
- LLM 可以只回一个表情包（`REACT`），不发大段文字
- LLM 可以在 COLD 状态下"看一眼手机，决定先不管"
- 用户不会看到后台的思考和状态切换

---

## 解决思路

### 1. 回复冲动抑制 + 双输出通道

**市面方案**：LLM 每次调用都生成回复文本，prompt 里写"少说话"——治标不治本。

**我们的方案**：同一个 LLM 在单次调用中输出两样东西：

```json
{
  "action": "WAIT",
  "items": null
}
```

- `action`：给系统看，决定这一轮的行为（WAIT / REPLY / LIGHT_ACK / REACT / ENTER_CHAT / END_CHAT）
- `items`：给转发层看，表示一组有序发送单元。为 `null` 或空时用户无感；非空时可混合文本、表情包和内部表情检索项。每个 item 只使用一个字段：`text`、`meme` 或 `search_meme`。

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  用户输入    │ ──▶ │  LLM 决策     │ ──▶ │  转发层      │
│             │     │ {action,items}│     │ items为空?   │
└─────────────┘     └──────────────┘     └──┬───────┬───┘
                                            │       │
                                         null    "来了"
                                            │       │
                                        用户无感   发送到对话
```

- `WAIT`：用户还没说完，等。`items:null`，buffer 不清空。
- `LIGHT_ACK`：短回应，"嗯，你说。"——不展开，不抢话。
- `REPLY`：正常文字回复，可连续发送一条或多条文本。
- `REACT`：表情参与型回应，可以是纯表情，也可以混合“文字 + 表情包 + 文字”，但必须至少包含一个 `meme` 或 `search_meme`；emoji 作为普通 `text`。
- COLD 下 `LIGHT_ACK` 和纯 `REACT` 是低负担回应，不代表进入热聊；展开文字回复或文字+表情混合回复需要 `ENTER_CHAT`。

---

### 2. COLD / HOT 双态系统

**市面方案**：AI 要么永远在线（秒回），要么离线（不回）。缺少中间态。

**我们的方案**：两种状态，由系统行为和 LLM 决策共同驱动，用户感知到的只是聊天行为的差异。

```
         COLD（离线生活态）                      HOT（热聊在场态）
   ┌──────────────────────┐          ┌──────────────────────┐
   │ • 消息先进入缓冲      │  触发：   │ • 收取频率显著提高    │
   │ • 附带冷启动元信息    │  拍一拍   │ • 仍保留回合闭合判断  │
   │   给 LLM 自己判断    │  ────▶   │ • 可以短句/表情/轻回应│
   │ • WAIT = 不看，保持   │  ENTER   │ • 不逐条抢答          │
   │ • 轻回应可见但保持    │  _CHAT   │                     │
   │                    │          │ 一段时间无互动后自动退回 │
   └──────────────────────┘          └──────────────────────┘
```

**关键设计**：COLD 状态不是"不处理"，而是给 LLM 附加上下文：

```json
{
  "timestamp": "10:00",
  "last_user_message_age": "24h ago",
  "status": "COLD",
  "user_text": "我今天真的很无语"
}
```

LLM 知道"用户上一次说话是昨天"，然后自己决定：现在该不该回应，还是继续等。用户看到的行为是自然的，不是状态标签。

---

### 3. 拍一拍/戳一戳：比"回复我"更自然的强制激活

用户发消息 = 普通信号，进入缓冲。
用户拍一拍 = 强制信号，"我现在需要你"。

这个交互来自 QQ/微信的日常用法，不需要额外解释：

```
用户：我今天真的很无语
用户：老板又发疯了
用户：我都不知道怎么说
                                    ← 角色还在 COLD 状态，没回应
用户：（拍一拍）
                                    ← 强制刷新注意力，立刻读 buffer
角色：我刚看到，细说。
```

---

### 4. 实时事件门（EventGate）+ 快照机制

多个机制需要协同：消息缓冲 + 用户继续输入 + 撤回 + 主动消息 + 拍一拍。如果直接交给 LLM 框架管理，很容易出现"旧回复在新消息之后发出"的割裂。

**EventGate 只做一件事：这条回复现在还能不能发。**

```
平台事件
    │
    ▼
┌──────────────┐
│  EventGate   │  命令分流 /mem /forget
│              │  维护 buffer_version
│              │  生成 snapshot_id
│              │  保证 single-flight
└──────┬───────┘
       │ stable snapshot
       ▼
┌──────────────┐
│  LangGraph   │  build_context → call_llm → harness → route_action
│  决策图       │
└──────┬───────┘
       │ ActionDecision
       ▼
┌──────────────┐
│  EventGate   │  复核 snapshot 是否仍有效
│  复核         │  发送幂等检查
└──────┬───────┘
       │
       ▼
   转发层 → 用户可见 / items 为空则静默
```

EventGate 不判断情绪、不改写文本、不做假延迟回复。它的职责和 LLM 的职责完全分开：

```
EventGate：这次结果现在还能不能发
LangGraph：这次如果要处理，应该怎么思考和决策
```

这对分工保证了 LLM 可以专注于做好"理解"和"表达"，而发送时机的工程一致性由代码确保。

Action Harness 是发送前的协议边界：只接受可解析、可校验、可执行的 `action + items`，错误输出最多修复一次，失败则安全降级。

### 5. 记忆系统重设计

**市面方案**：向量库存储记忆，用户看不到、改不了、不知道模型为什么记住了某件事。  
存储使用实时异步线程，太重且稳定性极弱。  
有可能出现记忆泄露："" 根据我的记忆，你不喜欢吃辣椒。""

**我们的方案**：两层 Markdown 文件，用户可直接打开阅读和编辑。

```
┌─────────────────────────┐
│   当天聊天上下文         │
└───────────┬─────────────┘
            │ 定时记忆分析任务（日间/晚间各一次）
            ▼
┌─────────────────────────┐
│  dm/2026-06-17.md       │  ← 每日可读摘要：今日大事、重要事实、相处习惯等固定结构
│  当天记忆文件           │
└───────────┬─────────────┘
            │ 凌晨 3-4 点整理线程
            ▼
┌─────────────────────────┐
│  MEMORY_CORE.md         │  ← 长期核心记忆：只有真正重要的才进来
│  永久核心记忆           │     被读入每日聊天上下文
└─────────────────────────┘

辅助链路：
  raw chat log（JSONL）—— 完整审计、回放、排错，不参与记忆整理
  TOMORROW_TOPICS.md —— 明日主动消息候选池
  /mem 和 /forget —— 用户显式维护入口，优先级最高
```



### 但更关键的是：谁来纠正记忆？谁在维护记忆？

假如你和你的赛博朋友已经相处很融洽了，但突然对面说了一句离谱的话——你不得不停下来纠正它。如果此时仍然用和朋友聊天一样的自然语言去批评它，会产生两个微妙但致命的问题：

**信任感崩塌**——"它这次说知道了，是真的记住了吗？下次还会不会又犯？"  
**身份割裂**——更难受的是，你被迫从"朋友"切换到"管理员"，刚才还聊得好好的，一瞬间温馨感全无。

这就是为什么我们引入了另外一个以命令号切换的外部记忆系统：**`/mem` 和 `/forget` 不是"命令行"，而是身份切换开关**：
<h3 align="center"><i>朋友负责陪你。</i></h3>
<h3 align="center"><i>系统负责记忆。</i></h3>

```
聊天模式（自然语言）                  维护模式（/mem /forget）
─────────────────────              ─────────────────────
用户：你别老催我睡觉                 用户：/mem 我不喜欢被催睡觉
角色：好吧好吧，不催了               系统：已存入记忆。
                                    ↓
      ↑ 真的记住了吗？                  硬写入 MEMORY_CORE.md
      下次还会再犯吗？                  用户可随时打开文件确认
```

当你敲下 `/mem` 的时候，你不仅开启了一个额外的硬记忆系统，更为自己打开了一个**身份自然转换的通道**：
- **心理减负**：不需要在"朋友"的面具下尴尬地批评对方——你使用指令开启了记忆后台，你正在面向配置系统。
- **硬触发**：命令通过记忆专员写入文件，无需担心"它有没有真的理解"——打开 `MEMORY_CORE.md` 就能亲眼确认。
- **确定性反馈**：系统回复"已存入记忆"，不是朋友在敷衍，而是系统工程师告诉你答案。

### 6. 主动消息：从未闭合话题来，不是从cosplay猫娘来

**市面方案**：定时提醒、"我想你了"、沉默召回——本质是留存工具。

**我们的方案**：主动消息的来源只有三个，按优先级排列：

```
未闭合话题（优先）
  └─ 用户提到但没结果的事："你明天跟他说了吗？"
      ↓
昨日记忆
  └─ 情绪余波、可自然承接的上下文
      ↓
生活感消息备选（低频、低压）
  └─ 轻轻出现，不假装强烈想念
```

硬约束：
- 用户没回复 = 当天不再发第二条
- 不用"你怎么不理我"这种情绪绑架文案

---

### 7. 表情包系统：参考Agent方案，使用工具分类召回 + 语义文件名精确选图

**市面方案**：随机从分类抽一张，或者用复杂向量检索。

**我们的方案**：两轮协议，先检索后精确。

```
LLM 第一轮：判断语境 → 输出 search_meme item
  例如：{"search_meme":"helpless:cry tired"}
              │
              ▼ 系统拦截（不发给用户），在分类目录按语义文件名匹配
              │ 返回候选：["helpless_miku_cry_floor", "helpless_cat_facepalm", ...]
              ▼
LLM 第二轮：从候选中选择 → 输出 meme item
  例如：{"meme":"helpless_cat_facepalm"}
              │
              ▼ 转发层精确匹配文件，转发图片
```

文件名即语义索引：`helpless_miku_cry_floor`。分类固定 18 类（amused / distress / observing / helpless / smiling ...），入库用多模态 LLM 生成语义化文件名，偷表情静默保存不打扰用户。

### 备注. 鲁棒性：核心体验不绑定任何单一能力

```
核心链路（缺一不可）        增强能力（不可用时自动降级）
─────────────────────    ──────────────────────────
WAIT / REPLY / LIGHT_ACK   表情包 → 降级短文本 / WAIT
MEMORY_CORE.md              图片理解 → 轻问或 WAIT
dm/YYYY-MM-DD.md            拍一拍 → 仍保留普通消息触发
TOMORROW_TOPICS.md           记忆检索 → 回退 Markdown 记忆
SOUL.md                      语音 → 文字替代
```

降级原则：错误进日志，不进聊天。用户感受到的是行为变化，不是技术错误。

## 架构总览

```
  QQ / 微信 / WebUI
         │
         ▼
    平台适配层（统一 ChatEvent）
         │
         ▼
  ┌──────────────┐
  │  EventGate    │  ← 实时事件门：缓冲、快照、single-flight、撤回、幂等
  └──────┬───────┘
         │ ConversationSnapshot
         ▼
  ┌──────────────┐
  │  LangGraph   │  ← 主回复决策图：构建上下文 → 调用 LLM → Harness → 路由
  └──────┬───────┘
         │ ActionDecision { action, items }
         ▼
  ┌──────────────┐
  │  EventGate   │  ← 复核 snapshot 有效性
  │  复核         │
  └──────┬───────┘
         │
    items为空? ──Yes──▶ 静默，用户无感知
         │
        No
         │
         ▼
    转发层 → 用户可见消息

后台任务（不在实时链路中）：
  定时记忆分析 → dm/YYYY-MM-DD.md
  凌晨整理线程 → MEMORY_CORE.md + TOMORROW_TOPICS.md
  主动消息调度 → 读取 TOMORROW_TOPICS.md → 经 EventGate 检查后发送
```
